# Работа, спринты и релизы UMD

Основная рабочая ветка — `master`. `VERSION` хранит целевой номер версии,
первоначально `0.1.0`. GitHub Actions используют Python 3.12 и существующие
секреты `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.

## Экшены

В GitHub → **Actions** выберите экшн → **Run workflow**.

| Экшн | Запуск | Результат |
| --- | --- | --- |
| **Start work** | Только вручную, при начале работы над проектом | Проверяет настройку CI, записывает начало работы, отправляет уведомление в Telegram. Можно указать комментарий. Не создаёт спринт и не меняет версию. |
| **Update master** | При push в `master` или вручную | Проверяет правила версий и тесты. При ручном запуске `source_branch` позволяет слить завершённый спринт в `master`; пустое поле проверяет текущий `master`. После успешного обновления собирает и публикует бету. |
| **Publish release or beta** | Вручную или из Update master | `beta` публикует следующую бету; `stable` публикует полноценный релиз; `cleanup` удаляет беты уже выпущенной версии. |
| **CI** | На pull request в `main`/`master` или вручную | Проверяет правила релизов, версию и Python-тесты. |

Владелец репозитория должен установить **Settings → Branches → Default branch**
(в текущем интерфейсе настройка также может находиться в General) в `master`.
При первоначальной настройке GitHub использовал `main`; копия экшенов размещена
и там, чтобы ручные запуски были доступны до смены основной ветки.
После смены основной ветки используйте `master` для изменения экшенов.

## Правило спринтов

1. Ветка спринта создаётся от актуального `master`, например `sprint/001`.
2. Каждый завершённый спринт интегрируется в `master` через PR или экшн
   **Update master** с `source_branch=sprint/001`.
3. До явной команды полноценного релиза все спринты сохраняют одну целевую
   версию: `v0.1.0-beta.1`, `v0.1.0-beta.2`, `v0.1.0-beta.3`.
   Дополнительные push в `master` тоже создают беты. Номер беты автоматически
   выбирается по существующим тегам и релизам этой версии.
4. Когда версия готова, вручную запустите **Publish release or beta**,
   `channel=stable`. Текущий коммит `master` должен иметь успешную опубликованную
   бету. Результат — `v0.1.0`.
5. После успешного stable можно удалить беты: включите `cleanup_betas` при
   публикации или отдельно запустите `channel=cleanup`.
   `cleanup_version=0.1.0` позволяет очистить старую версию после перехода
   к следующей. Пустое поле означает текущую `VERSION`.
6. Только теперь меняйте `VERSION`, например на `0.1.1` или `0.2.0`, и начинайте
   следующий цикл. Выбор patch/minor/major зависит от изменений приложения.

Проверка истории `VERSION` запрещает увеличение без опубликованного stable
предыдущей версии, уменьшение и неоднозначные номера. После stable новые беты
того же номера запрещены. Удалять беты необязательно для повышения версии.
Очистка удаляет GitHub prerelease и их beta-теги только выбранной версии;
стабильные релизы и теги сохраняются. Временные Actions artifacts истекают
через 30 дней; очистка GitHub Releases не удаляет их досрочно.

Если два обновления `master` происходят во время сборки, устаревшая публикация
останавливается: повторите экшн для актуального коммита. Публикации
сериализованы одной группой concurrency. Стандартная concurrency GitHub может
заменить ожидающий запуск более новым; заканчивайте один спринт перед следующим.

## Подключение Python-приложения

Сейчас в репозитории нет приложения, поэтому **Update master** проверяет CI и
показывает, что автобета ожидает `pyproject.toml`. Ручная публикация без него
завершается с понятной ошибкой и не создаёт релиз.

Когда появятся исходники, добавьте `pyproject.toml` с PEP 517 build backend.
Сборка должна выполнять `python -m build` и создавать wheel и sdist в `dist/`.
Workflow устанавливает приложение и запускает `pytest tests`, если есть
каталог `tests`. Это публикация Python-дистрибутивов в GitHub Releases;
PyPI, установщики EXE и публикация в магазины не настроены.

Версия Python-пакета должна соответствовать сборке:

| GitHub tag | Python package version |
| --- | --- |
| `v0.1.0-beta.1` | `0.1.0b1` |
| `v0.1.0` | `0.1.0` |

Сборке доступны `UMD_BUILD_VERSION` и `SETUPTOOLS_SCM_PRETEND_VERSION` с этим
значением. Рекомендуемый build backend — setuptools с setuptools-scm и
динамической версией; приложение также может читать `UMD_BUILD_VERSION`
в собственном backend. Метаданные wheel и sdist проверяются: статическая
неверная версия блокирует публикацию.

Релиз сначала создаётся как draft, затем к нему прикрепляются все проверенные
артефакты и только после этого он публикуется. Если загрузка или публикация
упала, draft сохраняется для диагностики. Перед повторным stable проверьте
незавершённый draft и при необходимости удалите только его и его неопубликованный
тег. Полноценные опубликованные версии повторно не используются.

## Права и уведомления

- Проверки и Start work имеют `contents: read`.
- Обновление master и публикация имеют `contents: write` через `GITHUB_TOKEN`.
- Ручное слияние использует обычный push, без force; конфликт или запрет правил
  ветки останавливает экшн. При защите `master` выполняйте слияние через PR.
- `GITHUB_TOKEN` не может менять файлы workflows при push. Спринты с изменениями
  `.github/workflows/` сливайте самостоятельно через PR.
- Push, сделанный через `GITHUB_TOKEN`, не запускает новый push-workflow,
  поэтому Update master напрямую вызывает повторно используемый release-workflow.
- Telegram получает результат начала работы, обновления master и публикации
  или очистки. Ошибка Telegram выводится как предупреждение и не отменяет
  успешно выполненную операцию. Значения секретов не выводятся.
