# Работа, спринты и релизы UMD

`master` — разработка и беты. `main` — полноценные релизы и основная ветка
репозитория. `VERSION` содержит целевую версию, первоначально `0.1.0`.
До ручной команды полноценного релиза номер `X.Y.Z` между спринтами сохраняется.

## Экшены

В GitHub → **Actions** выберите экшн → **Run workflow**. Для ручных запусков
можно оставить выбранную ветку `main`: экшены сами используют текущий `master`,
а после команды stable — конкретный коммит `main`.

| Экшн | Запуск | Результат |
| --- | --- | --- |
| **Start work** | Только вручную, при начале работы над проектом | Проверка настройки, запись начала работы и уведомление в Telegram; необязательный комментарий. |
| **Update master** | Push в `master` или вручную | Проверки и Windows-сборка с публикацией беты. `source_branch` вручную интегрирует ветку завершённого спринта; пустое поле проверяет текущий `master`. |
| **Publish release or beta** | Вручную; beta также вызывается из Update master | `beta` — очередная бета из `master`; `stable` — последняя проверенная бета → merge в `main` → сборка и полноценный релиз из `main`; `cleanup` — очистка бет. |
| **CI** | Pull request в `main`/`master` или вручную | Проверки версий, правил релизов и приложения на Windows x64. |

Сборки используют Windows runner, Python 3.12 x64 и зависимости из
`pyproject.toml`. Start work использует Linux: он не собирает приложение.

## Цикл версии

1. Ветка спринта создаётся от актуального `master`, например `sprint/001`.
2. Завершённый спринт интегрируется в `master` через PR или **Update master**.
   Каждый успешный push создаёт следующую бету: `v0.1.0-beta.1`,
   `v0.1.0-beta.2` и так далее. Дополнительный ручной `channel=beta` тоже
   создаёт новую бету. Номер выбирается по тегам и релизам этой версии.
3. Для полноценного релиза вручную запустите **Publish release or beta**
   с `channel=stable`. Последняя опубликованная бета данной версии должна
   соответствовать текущему коммиту `master` и содержать проверенную Windows-сборку.
4. Экшн фиксирует коммит этой беты, проверяет результат слияния и сливает его
   в `main` через GitHub API. Дерево исходников результата должно в точности
   совпадать с деревом беты. Stable пересобирается из конкретного коммита
   `main` с версией `0.1.0`, проходит тесты и публикуется как `v0.1.0`.
5. После успешной публикации можно удалить беты этой версии: `cleanup_betas=true`
   при stable либо отдельный `channel=cleanup`. `cleanup_version=0.1.0`
   выбирает уже выпущенную версию; пустое поле означает текущую `VERSION`.
6. Только после опубликованного stable меняйте `VERSION` в `master`, например
   на `0.1.1` или `0.2.0`, и начинайте следующий цикл.

Проверка истории запрещает повышение без опубликованного stable предыдущей
версии, понижение и неоднозначные номера. После stable новые беты этого номера
запрещены. Опубликованные версии и теги не используются повторно. Очистка
касается только beta-релизов и beta-тегов выбранной версии, сохраняет stable
и не затрагивает другую версию. Удаление бет не обязательно для повышения номера.

## Windows-сборки

Каждая бета и полноценный релиз содержат:

- `UMD-vX.Y.Z[-beta.N]-windows-x64.zip` — портативное приложение с
  графическим `UMD/UMD.exe`, консолью `UMD/UMD-console.exe`, yt-dlp, Deno,
  gallery-dl, FFmpeg/FFprobe, Chromium, пресетами переименования и инструкциями запуска.
- `build-manifest.json` — версия, тег, SHA коммита, платформа, результат тестов
  и контрольная сумма ZIP.
- `SHA256SUMS.txt` — SHA256 приложения для проверки скачанного архива.

Пользователь распаковывает весь ZIP и запускает `UMD.exe`; установка Python,
yt-dlp или браузера отдельно не требуется. Windows x64 — первая поддерживаемая
платформа. `UMD.exe` открывает окно Qt без CMD: анализ URL, просмотр метаданных,
выбор формата/качества, загрузки, очередь, история и настройки. Консольный
`UMD-console.exe` сохраняет диагностику и автоматизацию обработки метаданных.
Порядок вкладок канала без дат публикации определяется доступными данными
сайта; строгая хронология для таких источников пока не гарантируется.

Сборка запускает тесты, затем проверяет упакованный EXE командами `--version`,
`--self-test` и `--check-environment`; последняя проверяет комплектные инструменты
и запуск Chromium без обращения к внешним сайтам. FFmpeg/FFprobe проверяются
командой `-version`; gallery-dl — `--version` со сверкой фиксированной версии и SHA256.
Windowless EXE пишет результаты диагностики в JSON через
`--diagnostics-output PATH`. Дополнительно запускается настоящий упакованный
GUI (`--gui-smoke --diagnostics-output PATH --screenshot PNG`) с проверкой
видимого окна, Qt event loop, вкладок и инициализации очереди; сохраняется
снимок окна. Заголовки PE подтверждают x64 GUI subsystem у `UMD.exe` и console
subsystem у `UMD-console.exe`. Версия EXE, тег, SHA исходников,
контрольная сумма и содержимое ZIP проверяются до публикации. Wheel, архив
исходников и заглушки не считаются сборкой приложения.

Сборочное окружение изолирует PATH: в приложение попадают OpenSSL DLL
выбранного Python; их SHA256 сравниваются с исходными библиотеками.
Сетевые запросы Qt используют штатный Windows Schannel; сторонний Qt OpenSSL
backend не включается. GUI-проверка подтверждает доступность Schannel/TLS.
Windows ICU/UCRT/API-set используются из ОС, чтобы сторонние инструменты
на сборочном компьютере не подменили несовместимые системные DLL.

| GitHub tag | Версия приложения/Python |
| --- | --- |
| `v0.1.0-beta.1` | `0.1.0b1` |
| `v0.1.0` | `0.1.0` |

Сборка получает `UMD_BUILD_VERSION` и `SETUPTOOLS_SCM_PRETEND_VERSION`.
Локальный эквивалент: установка `.[dev,build]`, `python scripts/provision_tools.py`,
`python -m playwright install chromium` с `PLAYWRIGHT_BROWSERS_PATH=0`, затем
`python scripts/build_windows.py --version 0.1.0b1 --tag v0.1.0-beta.1`.
Результат находится в `release-dist/`.

## Краткие релиз-ноты

Текст берётся из `release-notes/X.Y.Z.md`: конкретные изменения и ограничения,
максимум восемь строк и 2000 символов. Перед завершением спринта обновляйте
этот файл, чтобы следующая бета отражала актуальные возможности версии.
Списки коммитов автоматически в релиз не добавляются.

## Защита процесса и повторный запуск

Публикации сериализованы одной concurrency-группой. Перед публикацией ветка
должна оставаться на собранном коммите; для stable также проверяется `master`.
Если ветка изменилась во время сборки, публикация останавливается. Дождитесь
проверенной беты актуального `master` и повторите команду. GitHub может заменить
ожидающий запуск более новым: завершайте один спринт перед следующим.

Релиз сначала создаётся как draft. Все проверенные файлы прикрепляются до
публикации. При ошибке загрузки draft сохраняется для диагностики: перед
повторным запуском удалите только незавершённый draft и его неопубликованный
тег. Успешно опубликованные релизы не заменяются.

Если сборка stable упала после слияния, `main` уже содержит исходники беты,
но полноценного релиза ещё нет. Исправления идут в `master`, публикуют новую
успешную бету, после чего повторяется ручная команда stable. `VERSION` до
успешной публикации stable остаётся прежней. Actions artifacts хранятся 30 дней;
очистка GitHub Releases не удаляет их досрочно.

## Права и уведомления

- CI и Start work: `contents: read`; обновление и публикация: `contents: write`.
- Автоматический stable разрешён только по `workflow_dispatch`, не по push
  и не через повторно используемый workflow.
- Слияния обычные, без force. Конфликт или запрет защиты ветки останавливает
  экшн; настройки защиты должны разрешать выбранный процесс.
- `GITHUB_TOKEN` не может изменять `.github/workflows/`. Проверенные изменения
  экшенов нужно отдельно зеркалировать в `main` до команды stable, чтобы
  содержимое workflows в `main` и `master` совпадало. Это подготовка автоматики;
  код приложения попадает в `main` через ручную команду stable.
- Спринты с изменениями workflows интегрируйте в `master` через PR или своим
  авторизованным push; обычный токен экшена такое изменение не протолкнёт.
- Push через `GITHUB_TOKEN` не запускает новый push-workflow, поэтому
  **Update master** напрямую вызывает release-workflow для беты.
- Telegram использует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` из secrets.
  Начало работы, обновления и публикация/очистка присылают результат; CI
  уведомляет при сбое. Уведомление об опубликованной бете или полноценном релизе
  содержит краткие release notes и прямую ссылку на Windows x64 ZIP приложения.
  Ошибка Telegram даёт предупреждение без отмены операции
  и без вывода значений секретов.
